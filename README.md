# Transaction Anomaly Detection & Alerting Pipeline

Python · Flask · TLS · Statistical analysis · Alerting

A pipeline that reads card or account transactions, flags the suspicious ones using
**rule-based checks** and **statistical checks**, grades each by **severity (LOW, MEDIUM,
HIGH, CRITICAL)**, and serves the alerts through a **Flask API over TLS**. Every alert lists
the exact reasons it fired and how many points each reason added, so an analyst can audit it.

> The sample data in this repo is synthetic and generated by a script. Nothing here is
> real customer data.

## How it works

```
CSV file ──► validate ──► time-ordered scoring engine ──► alerts (score 0-100 + reasons)
JSON POST ─┘                  │                                  │
                              ├─ rule checks                     ├─ CLI report / JSON file
                              └─ statistical checks              └─ Flask API over HTTPS
```

Each transaction is judged only against what the pipeline knew *before* it arrived: the
account's earlier purchases, merchants, countries, and recent activity. Points from every
check that fires are added (capped at 100) and mapped to a severity.

| Severity | Score |
|----------|-------|
| LOW      | 20-39 |
| MEDIUM   | 40-59 |
| HIGH     | 60-79 |
| CRITICAL | 80-100 |

Below 20 the transaction is not flagged.

### Checks

| Code | Type | Fires when | Points |
|------|------|-----------|--------|
| `HIGH_AMOUNT` | rule | amount >= 5,000 | 30 |
| `VERY_HIGH_AMOUNT` | rule | amount >= 10,000 (replaces `HIGH_AMOUNT`) | 45 |
| `ROUND_LARGE_AMOUNT` | rule | amount >= 1,000 and an exact multiple of 1,000 | 10 |
| `ODD_HOURS` | rule | 00:00-04:59 UTC and amount >= 500 | 15 |
| `FOREIGN_COUNTRY` | rule | country differs from the account's most common country (needs 5+ past transactions) | 15 |
| `NEW_MERCHANT_HIGH` | rule | first purchase at a merchant and amount >= 1,000 (needs 5+ past transactions) | 10 |
| `VELOCITY` | rule | 5 or more transactions on one account within 10 minutes | 25 |
| `GEO_JUMP` | rule | country changes within 60 minutes of the previous transaction | 30 |
| `DUPLICATE` | rule | same merchant and amount repeated within 2 minutes | 20 |
| `AMOUNT_OUTLIER` | statistical | robust z-score of the amount, against the account's own history, is >= 4.0 | 25 |
| `AMOUNT_OUTLIER_EXTREME` | statistical | robust z-score >= 6.0 (replaces `AMOUNT_OUTLIER`) | 40 |
| `GLOBAL_AMOUNT_OUTLIER` | statistical | new account (under 5 transactions) with an amount above Q3 + 3 x IQR of all accounts | 20 |

**Robust z-score.** The pipeline takes the logarithm of past amounts, finds their median and
median absolute deviation (MAD), and measures how far the new amount sits above that
median. Median and MAD are not distorted by a few earlier outliers, and the log suits
money amounts, which are skewed. A floor on the spread stops near-identical histories
from making tiny changes look huge.

All thresholds and points live in `anomaly_pipeline/config.py` (`ScoringConfig`).

## Quick start

Developed and tested on Python 3.13. The code is written to run on Python 3.9 or newer
(older versions were not available to test here).

```bash
python3 -m venv .venv
source .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

pytest                                  # run the whole test suite
```

### 1. Run the batch pipeline on the sample data

```bash
python scripts/generate_sample_data.py   # (re)creates data/*.csv, seeded and reproducible
python -m anomaly_pipeline.cli data/sample_transactions.csv \
    --labels data/sample_labels.csv --output out/alerts.json
```

Useful options: `--min-severity MEDIUM`, `--top 20`, `--output alerts.json`.
The input CSV needs these columns: `transaction_id, account_id, timestamp, amount, merchant,
country` (optional: `channel` = online/pos/atm, `category`). Timestamps are ISO-8601; values
without a timezone are treated as UTC. Bad rows are skipped and reported.

### 2. Serve the alert API over TLS

```bash
python scripts/generate_cert.py                   # self-signed cert for localhost / 127.0.0.1
export ALERT_API_KEY="choose-a-long-random-value" # optional but recommended
python -m anomaly_pipeline.server                 # https://127.0.0.1:5443
```

The server needs a certificate and key and refuses to start without them. Use
`--generate-cert` to create them on the fly, or `--insecure-http` for plain HTTP during
local debugging only. TLS 1.2 or newer is enforced.

In a second terminal:

```bash
# Replay the sample transactions through the running server and show the top alerts
python scripts/demo_client.py --cacert certs/server.crt --api-key "$ALERT_API_KEY"

# Or call it directly
curl --cacert certs/server.crt https://127.0.0.1:5443/health

curl --cacert certs/server.crt -H "X-API-Key: $ALERT_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"transaction_id":"T1","account_id":"ACC1","timestamp":"2026-09-10T02:15:00Z",
          "amount":12500,"merchant":"Gem Store","country":"CA"}' \
     https://127.0.0.1:5443/transactions

curl --cacert certs/server.crt -H "X-API-Key: $ALERT_API_KEY" \
     "https://127.0.0.1:5443/alerts?min_severity=HIGH&limit=10"
```

If you did not set `ALERT_API_KEY`, leave out the `X-API-Key` header and `--api-key`.

## API

If `ALERT_API_KEY` is set, send it in an `X-API-Key` header on every route except `/health`.

| Method & path | Purpose |
|---------------|---------|
| `GET /health` | liveness check |
| `GET /stats` | transactions processed, alert counts by severity |
| `POST /transactions` | score one transaction (object), or a batch (list, or `{"transactions": [...]}`, max 1,000). Returns a score, severity and reasons for each. Raises an alert when the severity is LOW or higher |
| `GET /alerts` | list alerts, highest score first. Query: `min_severity`, `account_id`, `limit` (1-500), `offset` |
| `GET /alerts/<id>` | one alert with its full list of reasons |

Behaviour worth knowing:

- Transactions are scored **in the order received**. Send them oldest first, as the
  behavioural checks depend on earlier activity.
- A batch is **all or nothing**: if any item is invalid, nothing is scored (HTTP 400, with
  the index of each bad item).
- A repeated `transaction_id` is rejected with HTTP 409.
- Errors are JSON. Unexpected failures return a generic 500 and never expose internals.

Example alert:

```json
{
  "alert_id": "A-000021",
  "severity": "CRITICAL",
  "score": 85,
  "transaction": { "transaction_id": "T002068", "account_id": "ACC021", "amount": 14515.51, "country": "GB", "...": "..." },
  "reasons": [
    { "code": "VERY_HIGH_AMOUNT", "kind": "rule", "points": 45,
      "description": "Amount 14,515.51 is at or above the very-high limit of 10,000" },
    { "code": "AMOUNT_OUTLIER_EXTREME", "kind": "statistical", "points": 40,
      "description": "Amount is extremely high for this account (robust z-score 10.8)" }
  ]
}
```

## Results on the bundled sample data

The generator creates about 2,100 transactions across 23 accounts, including 51 injected
anomalies of six kinds. Running the pipeline on that file (seed 42) gives:

| Measure | Value |
|---------|-------|
| Precision | 0.814 |
| Recall | 0.686 |
| False-positive rate on normal transactions | 0.39% |

| Injected anomaly | Flagged |
|------------------|---------|
| Very large purchase | 6 / 6 |
| Unusually large for the account (under the fixed limits) | 5 / 5 |
| Impossible travel (country change in 20 minutes) | 4 / 4 |
| Night-time purchase abroad | 4 / 4 |
| Duplicate charge | 4 / 4 |
| Rapid burst of small purchases | 12 / 28 |

The burst figure is expected: each burst has 7 transactions, but the velocity rule needs
5 within 10 minutes, so only the 5th onward can trip it. These numbers describe
**synthetic data built to contain these patterns**; they show the checks behave as designed,
not how the pipeline would perform on real transactions. Real data would need threshold
tuning against labelled cases.

```
  config.py     ScoringConfig: every threshold and point value

```

## Security notes and limitations

- **TLS:** the included certificate is self-signed and meant for local use. Clients must
  trust it explicitly (`--cacert certs/server.crt`). For a real deployment, use a
  certificate from a trusted CA. Keep `certs/server.key` private (it is git-ignored and
  written with mode 0600).
- **API key:** a single shared key compared in constant time. Fine for a demo; a real
  deployment would want per-client credentials.
- **Server:** this runs Flask's built-in server, which is not meant for production. Put the
  app behind a production WSGI server and a TLS-terminating proxy instead.
- **State is in memory.** Account history and alerts are lost on restart, and the API is
  a single process. The alert store is not a database.
- Hours are evaluated in UTC, and "home country" is the most common country seen for the
  account so far, so travellers will produce `FOREIGN_COUNTRY` hits.
- Rules and thresholds are hand-set. This is a transparent rules-plus-statistics design,
  chosen so every alert can be explained, not a trained machine-learning model.
